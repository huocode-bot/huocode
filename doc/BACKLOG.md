## IAM: `s3:DeleteObject` for Lambda roles (follow-up required)

The active-pointer design (`jobs/active/<owner>/<repo>/<sha>.json`) relies on `s3:DeleteObject`. It is
currently worked around in code (terminal refs are treated as absent, deletion failures are tolerated).
Details: see the JGit migration discussion (09-2026).

- Worker role: `s3:DeleteObject` on `jobs/active/*`
- API role: `s3:DeleteObject` on `jobs/*` (expired job purge in `AnalysisJobService.getJob`)

If roles are regenerated by a Poja deployment, this policy must be added to the Poja source of truth
(or re-applied after each deployment).

## Scale: high threshold + parallel PMD

- `huocode.hard-file-limit` is 3000 (sequential, fits within the 600s Lambda timeout).
- To target 10k+ files: worker memory >= 2048 MB (done) **and** bounded parallel PMD
  (4-8 thread executor). Then validate with a large synthetic repo.

## Orphaned active refs

As long as there is no IAM `s3:DeleteObject`, the bucket accumulates terminal active pointers
(harmless to the code, invisible in metrics). Manual or automated cleanup to be planned.

## Worker tuning (Poja console)

- `batch` on the analysis worker: 1 (JGit+PMD jobs are long and memory-hungry; Poja runs the batch in
  parallel sharing the same heap/timeout — 2048 MB and 600s shared).
- Worker memory 2048 MB, API 1024 MB: validated.
- `reserved concurrency` 5: OK.

## `.gitignore` ritual

outside the repo (`../huocode.secret.txt`) for Poja import. After each Poja regeneration, re-add the
line if the file reappears at the root.
